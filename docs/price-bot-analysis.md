# 价格机器人：抓进球信号的实测复盘（2026-08-26 ~ 08-30）

这份文档给下一轮分析当基线。它记录的是**已经量过的事实**、**踩过的坑**、以及**这一轮改了什么**，
好让下次不必从零再挖一遍。数据窗口是 8/26 10:44 ~ 8/30 18:36（UTC），207 条规则。

---

## 1. 目标与判定标准

策略目标：**抓其他聪明资金的动向**。抓对了意味着进球。

所以「正确买入」的判定窗口是 **60 秒**，不是 30 分钟。用户明确定过这条线：
> 「正确买入，判断时间太长了，1min2min 内也许是正确的，如果超过这个时间就是伪正确。」

据此分五类：

| 桶 | 含义 | 判定 |
|---|---|---|
| A 正确买入 | 买入后短时间内进球 | 成交后 **≤60s** 价格涨到高位（≥0.95） |
| B 边缘 | 慢了一点 | 60~120s 内涨到高位 |
| C 伪正确买入 | 方向对但不是「抓动向」 | >120s 才涨上去 |
| D 错误买入 | 没进球，价格归零 | 窗口内最低价跌到谷底 |
| E 错误未涨 | 买了但没动 | 价格横着 |
| 正确未买入 | 闸门拦对了 | 有买入信号被拦，且事后没有真进球 |
| 错误未买入 | 闸门拦错了 | 有买入信号被拦，但事后真进球了 |

**判定「赢/亏」用链上结算，不要用价格。** 上表的分桶用于刻画*快慢*，
但胜负必须读 `price_bot_rules.settled_outcome`（`syncRuleOutcomes()` 回填的链上真相）。
历史上用过的两个代理口径都是错的：

- **价格日志出现过 `bid >= 0.99`** —— 有 10 个假阴性（链上结算为 YES，但监控在价格涨上去
  之前就停了，最高 bid 只到 0.60~0.98）。它曾经看起来精确率 100%，那是只有 4 条
  可结算亏损造成的假象。详见 9.18。
- **价格日志收在 0 附近** —— 退市假象。11 条序列从 0.999 直接跳到 0.000，
  规则 329 链上结算是 `[1,0]` 却收在 0.000。

而**盈亏**要用入场价算：赢 = `1 − 入场价`，亏 = `−入场价`。胜率和钱不是一回事——
0.988 均价下赢 89% 是亏 −0.0953（9.18.2 有整表）。

用户定的场景前提（决定了为什么胜率上限是 100%）：
> 「我所有盘口都是确定的，只要进一球就会结束盘口，我们的目的是吃到进球后
> 对的确定性的大小球盘口的红利。」

即所有盘口都贴在临界线上，一球即结算，所以**亏损只可能来自假阳性**，
理论天花板是 100% 胜率。
> ⚠ **但「进球后」这个前提在执行层面从未成立**：123 笔下单里 0 笔发生在价格到过 0.99
> 之后，中位数领先进球 16.7 分钟（9.21b，图见 `docs/price-bot-signal-charts.html`）。
> 实际在做的是「还会再进一个球」的方向性押注，不是确定性套利。真实 `goal_surge` 触发做到 85.3%（n=109，100% 结算覆盖），
盈亏平衡线是 78.1%（= 均价 0.7809），EV +0.0723 且 CI 整体为正。
链上实盘核对（9.21）：47 个真实成交仓位 40 胜 7 负，净 +$12.33 / ROI +5.4%，
方向一致但每笔边际比上面低约三成——上面按 `placed` 统计，而 placed 不等于成交。

## 2. 实测结果

### 2.1 成交结果分布（28 笔 placed，按规则去重，共 $139.96）

| 桶 | 笔数 | 占比 |
|---|---|---|
| A 正确买入（≤60s） | **2** | 7% |
| B 边缘（60~120s） | 2 | 7% |
| C 伪正确（>120s 慢涨） | **16** | 57% |
| D 错误买入（跌到谷底） | 3 | 11% |
| E 横盘 | 5 | 18% |

只有 2/28 真正抓住了进球瞬间：
- 规则 384：信号时 0.63 → 60s 内 0.99，买在 0.74
- 规则 288：信号时 0.90 → 0.99，买在 0.93

两笔都是**在涨势中途**触发的，不是涨完才追。

C 桶里有几笔中途探得很深（规则 283 最低 0.01、规则 329 最低 0.00、规则 381 最低 0.17），
最终盈利属于运气，不能算策略有效。

### 2.2 闸门归因（按 规则+闸门 去重 = 独立决策）

| 闸门 | 独立决策 | 其中事后真进球 | 错拦率 |
|---|---|---|---|
| 买入价上限 | 56 | 29 | **60.7%** |
| 价差上限 | 11 | 6 | 54.5% |
| 买入价下限 | 12 | 3 | 25.0% |
| 未授权 | 18 | 4 | 22.2% |
| 单盘口笔数上限=1 | 21 | 2 | 9.5% |
| 最小份数/金额 | 4 | 4 | **100%** |
| 余额不足 | 4 | 0 | 0% |

订单表口径对得上：1631 skipped + 28 placed + 16 failed = 1675，
与各闸门计数 623+464+214+158+155+28+16+15+2 完全相等，没有漏项。

### 2.3 信号根本不晚 —— 这是最关键的一条

一度以为「机器人太慢，价格到 0.99 之后才发信号」。**测量否掉了这个判断**：

- 50 次真实上涨中，**晚于涨势的信号 = 0 次**
- 25 次信号早于涨势，7 次同刻（±2s）
- 中位领先 **83 秒**
- 全部 3699 条信号里，触发时 bestBid ≥0.99 的只有 325 条（8.8%）

信号侧是好的。问题在**定价**和**基础设施**，不在判断时机。

### 2.4 涨势形态：有充足的介入窗口

50 次上涨中：
- 15 次是一步跳（其中若干从 0.00 起跳，是结算清盘或断联后的假跳，**不能算真信号**）
- **35 次是多步爬升**，在 0.80~0.95 区间停留：中位 1820s，p25 70s，p75 3130s，中位 62 个采样点

也就是说，绝大多数机会有几十秒到几十分钟的介入窗口。

### 2.5 漏检

- 50 次真实 <0.90 → ≥0.95 上涨，信号覆盖 31 次，**漏 19 次（38%）**
- 漏的集中在 8/27 15:30 ~ 8/28 18:30，正是采样断档期 —— **漏检主要是采样没跑，不是算法看不见**

## 3. 根因

### 3.1 定价基准错配（已修）

定价用 `bestAsk + slippageBuffer`，而触发判断和 `minBuyPrice` 用 `bestBid`。
宽价差盘口（bid 0.85~0.90 / ask 0.97）算出的限价直接顶到 0.99，撞上 `maxBuyPrice`。

所以那 486 次「限价0.9900 ≥ 上限0.97」**不是涨完了，是价差宽**。
那种价位买进去赢了只赚 1%、错了归零，赔率极差。

### 3.2 归因被掩盖（已修）

宽价差盘口会同时触发「价差上限」和「限价上限」两个闸，先撞哪个记哪个。
价差闸原本排在后面，导致大量薄盘被记成「利润空间不足」，价差闸的真实体量（158）被低估。

### 3.3 采样断档 = 进程重启后没人手动点启动（已修）

这是最初误判的一条。原以为是 WS 断联，实测：

- 8/26~8/30 共 80 小时跨度，**46 小时完全没有 price_update**
- 连接事件表里**总共只有 2 条**：一次 disconnect（8/28 10:24:46）+ 一次 reconnect（11:00:21），
  downtime 2135644ms ≈ 36 分钟
- 断档窗口内其实有 6801 条 price_update —— 不是全局停采，是**特定规则**没在跑
- `startPriceBot()` 以前只在前端点「启动」时才调用，服务器 boot 时**从不自恢复**

207 条规则里 91 条采样为 0，81 条 ≥100 行，10 条 <10 行。

### 3.4 规模参数来自内存态，不是规则数据

`规模=3 usdc` 这类 skip 一度以为是规则级 `autoTradeParams` 覆盖。
查库确认：**`price_bot_rules.auto_trade_params` 全为 NULL，0 条规则有持久化覆盖**。
那是运行时全局配置（`PriceBotConfig` 内存态，从不落库），重启即回落到 `DEFAULT_AUTO_TRADE`。
所以不需要改数据。

## 4. 这一轮改了什么

| 项 | 改动 | 文件 |
|---|---|---|
| a | 盘口质量闸提到限价上限之前，宽价差归因到「价差过宽」而非「利润空间不足」 | `price-bot.ts` ~1498 |
| b | 新增 `maxPremiumOverBid`（默认 0.04），限价不得超过 `bestBid + 该值` | `types.ts`、`auto-trade.ts` |
| c | 查清规模参数来自内存态，**无需改数据** | — |
| d | `maxOrdersPerRule` 保持 1（错拦率仅 9.5%），**不放宽** | — |
| e | 服务器 boot 时自动恢复价格机器人监控与采样 | `server.ts` `restorePriceBot()` |

`maxPremiumOverBid` 的取舍：压回 bid 附近可能挂不上，但**挂不上远好过在 0.99 接盘**。
设 0 即退回纯 ask 穿价。无 bid 时不生效——没有共识价可参照，硬套上限会把价格压到无意义的位置。

`restorePriceBot()` 只恢复监控与采样，**不动自动下单总开关**：那个开关按设计每次重启都回到关闭，
需要人明确授权才会真下单。恢复失败不阻断 HTTP 服务。

测试：`npx tsx --test src/bots/price-bot/auto-trade.test.ts`，28 条通过（新增 5 条溢价上限用例）。

## 5. 下次分析要注意的坑

1. **别用最终价判胜负。** 结算后盘口被清空，`bestBid` 归 0，和真亏损无法区分。
   已识别 11 条结算清盘规则。**必须取窗口内最低/最高价，不能取最后一个价**。
2. **从 0.00 起跳的「一步跳」不是信号。** 那是结算清盘或断联后的假跳。
3. **信号与成交 join 会扇出。** 一笔成交能匹配上多条相邻信号，导致
   「配对上信号的 placed = 103 / 库里 placed 总数 = 28」。**按规则去重**后才是 28 笔 / $139.96。
4. **闸门计数要按 规则+闸门 去重**，否则同一个决策被反复计数。
5. **`price_update` 是时区基准。** 这些行一直由 `recordLogsBatch` 以 UTC 写入，
   且刻意排除在回填之外，是未被污染的真值。8 小时错位会表现为对它的 ±28800s 位移。
6. **当前数据不适合校准价值推断系统**：38% 漏检 + 采样断档，样本有系统性偏倚。
   要做方向二，得先攒一段采样完整的数据。
7. **先确认在量的是哪个 `rule_type`。** 生产的买入信号是 **`goal_surge`**
   （172 条 `buy_signal`，8 秒窗口 / 净涨 0.02 / 跳空 0.05）。`percent_change` 只有 3 条
   而且**全是 `alert`**。9.18 之前有整整六轮 EV 是在评估一个没在用的信号，全部作废。
   两者的入场价差 0.12（0.7809 vs 0.9033），足以让 EV 从 +0.065 翻成 −0.124。
8. **胜负口径必须是链上结算**，不能用价格代理。见第 1 节和 9.18。
   代理口径的假阴性会让 EV 系统性偏悲观。
9. **不要丢弃 outcome 未知的样本。** 未知样本里亏损占比显著偏高，
   丢掉它们会让多个分段结论**符号翻转**（9.18 之前「95+ 分钟最好 +0.2520」就是这么来的，
   那一段的 9 个未知样本后来全是亏损）。
10. **`soccer_events.end_time` 是开球时间，不是散场时间。** `start_time` 是盘口挂牌日期，
   常在开球前几周。`computeMatchStatus`（`src/soccer/db.ts`）自己就写着 `const kickoff = end.getTime()`。
   验证：78/79 个信号落在 `end_time` 之后 [−10, 130] 分钟内。
11. **`logged_at` 的时区陷阱有两种写法，别混用。** 当字符串读出来再补 `'Z'` 得到的是 UTC，
   但 mysql2 会把 `DATETIME` 列解析成服务器本地时间（UTC+8）的 JS `Date`。
   两种混用会产生 480 分钟偏移。统一用
   `DATE_FORMAT(col, '%Y-%m-%d %H:%i:%s')` 取**两边**。
12. **`price_bot_orders.status='placed'` 不等于成交**，只表示交易所受理了。
   66 个 placed token 里 20 个链上零成交（挂着没成交、规则完结时被撤）。
   按 placed 算 EV 会高估三成，见 9.21。成交真相在
   `soccer_orders.order_status`（`filled` / `settled` 才算，排除 `cancelled`）。
13. **算 EV 前先确认有没有中途卖出。** 所有 EV 都假设持有到结算；
   账上实际有 23 笔卖出，少数割在 0.50~0.83（9.21）。有卖出就是另一个口径。
14. **`settled_outcome` 是小写 `yes`/`no`**，比大写会静默得到 0 胜 0 负。
15. **同一批下单在两张表里时间差 8 小时**：`soccer_orders.created_at` 是本地时间（UTC+8），
   `price_bot_orders.created_at` 是 UTC。会被误认成两个不同的下单来源。
16. **链上流水按 `conditionId` + `outcomeIndex` 归组，不要按 `asset`。**
   `data-api` 的 REDEEM 记录 46 条里只有 13 条带 `asset`，按 `asset` 归组会丢掉
   33 笔赎回，把 +$12.33 算成 −$111.67（9.21）。
17. **这个钱包是多条下单路径共用的。** `price_bot_orders` 只做 O/U；
   让分/赢球/平局/双方进球来自 `soccer_orders`。归因不分开就会把别人的亏损算到信号头上。

## 9. 止损与挂单入场的测量结论

这一节回答两个问题：**在 0.95 挂单等成交可行吗**、**止损能不能真的执行**。
四个脚本 `m1maker.mts` / `m2stop.mts` / `m3dip.mts` / `m4empty.mts`，口径同第 2 节。

先记住入场价决定的门槛，后面所有数都要对着它看：

| 入场价 | 赔率 | 盈亏平衡胜率 | 按实测 71% 胜率的期望值/份 |
|---|---|---|---|
| 0.95 | 19:1 | 95% | −0.24 |
| 0.85 | 5.7:1 | 85% | −0.14 |
| 0.74（规则 384 实际成交价） | 2.8:1 | 74% | −0.03 |

### 9.1 挂 0.95 买单：机制成立，但方向是反的

> 本节测的是**固定价位 0.95** 的挂单。9.14 换成**相对报价**（跟随 bid + 1 tick）
> 重测了整个买入方式问题，结论细化：逆向选择的代价可量化为 −0.0741/笔，
> 而价格优势 +0.0822 恰好抵掉九成。本节末尾「问题不在挂单方式」这句要读作
> 「不在挂单方式**能否省钱**」——它确实省，只是省下的被筛选代价吃掉。

样本取「信号时 ask 已 >0.95」的 37 条规则，也就是当前被利润空间闸门拦下来的那批。

| | 次数 | 占比 | 最终到 0.99 的比例 |
|---|---|---|---|
| 挂上了（后续 ask 下探 ≤0.95） | 16 | 43.2% | **68.8%** (11/16) |
| 挂不上（ask 再没回到 0.95 以下） | 21 | 56.8% | **85.7%** (18/21) |

成交等待时长中位 40 秒（p25 12s / p75 261s / 最长 2772s）。

**逆向选择被证实。** 挂不上的胜率比挂上的高 17 个百分点——能成交恰恰因为有人愿意在 0.95
出货，而那更多发生在判断错的时候。成交组期望值 **−0.26/份**（赢 11×+0.05，输 5×−0.95），
对着 0.95 需要的 95% 门槛，实测 68.8% 差得很远。

要注意另一半：挂不上的那 21 次里 18 次涨到了 0.99，这些是真机会，
但**它们的 ask 一直在 0.95 之上，任何 ≤0.95 的买单都拿不到**。想吃这批只能以 0.99 接盘，
那需要 99% 胜率。两条路的期望值都是负的，问题不在挂单方式，在入场价位。

### 9.2 下跌比上涨跳空得多

从 ≥0.88 跌到 ≤0.60 的 30 段：

| 形态 | 段数 |
|---|---|
| 真跌（有中间档位，单步 <0.25） | 6 |
| 跳空（单步跌幅 ≥0.25） | 19 |
| 结算清盘（跌到 0 且不恢复、在轨迹末端） | 5 |

- 25 段可作止损样本里，只有 **14 段（56%）** 跌途经过 0.80~0.88 这种可卖档位。
  这个 56% 就是「止损单能真的出掉」的上限，另外 44% 跌的时候下方没有能成交的价位。
### 9.3 84% 的下跌后来又涨回去了

这是本轮最有决定性的一个数：25 段可交易下跌里 **21 段（84%）**之后又回到 ≥0.95。
换个口径单独量「跌破 0.60 的下探」，45 段里 30 段（66.7%）恢复到 ≥0.88，其中：

- **单点坑**（只有 1 个采样低于 0.60，前后都正常）= 11 段，占恢复组 36.7%
- 10 秒内就恢复 = 10 段，占 33.3%
- 恢复组低位停留时长：中位 28s、**p25 只有 1s**、p75 168s

也就是说下跌里有相当一部分是**买盘一侧瞬时抽空**：最优买单被撤，下一档远在低位，
1 秒后又补回来。这类时刻挂着价格止损，会在谷底把仓位倒掉，随后价格回去。

要区分清楚两种形态，它们的处理方式相反：

| 形态 | 特征 | 处理 |
|---|---|---|
| 买盘瞬时抽空 | bid 掉到 0.18~0.55，**ask 仍在 0.93~1.00** | 忽略，等一个确认窗 |
| 结算清盘 | bid=0 且 ask=1.00，前一帧多为 ≥0.97 | 必须排除，这是已赢 |

第二种要特别小心：15 段「再没恢复」里有 **11 段是 `1.00 → 0.00` 的结算清盘**，
前一帧价格是 1.00，这些是**赢了的单子**。按价格判断会把它们全当成归零亏损处理掉。

### 9.4 价格止损的期望值是负的

拿确认时间窗做敏感性测试（触发条件：bid 跌破 0.60 且持续超过窗口长度）：

| 确认窗 | 触发次数 | 误触发（后又涨回） | 真止损 | 漏掉的真亏 |
|---|---|---|---|---|
| 0s | 34 | 30 | 4 | 11 |
| 5s | 25 | 21 | 4 | 11 |
| 10s | 24 | 20 | 4 | 11 |
| **30s** | **18** | **14** | **4** | **11** |
| 60s | 13 | 10 | 3 | 12 |
| 120s | 8 | 8 | **0** | 15 |

注：「漏掉的真亏」里绝大部分是 9.3 说的结算清盘（`1.00→0.00`，实为已赢），
不是真的漏了亏损，所以这一列不该当成加长窗口的代价看。

最好的一档是 30s：**误触发 14 次换 4 次真止损**，误报率 78%。算期望值：

- 14 次误触发 × 约 −0.44/份（在 ~0.55 卖掉，价格随后回 ~0.99）= **−6.2**
- 4 次真止损 × 约 +0.40/份（在 ~0.40 出掉而不是归零）= **+1.6**
- 合计 ≈ **−4.6**

**价格止损在这份数据上是净亏的**，被瞬时抽空的误触发压死。加长确认窗能压低误报，
但 120s 时真止损降到 0——能等到确认的那些跌，早就跌穿了能卖的价位。

结论分两条，不要混：

- **价格止损不做。** 不是参数没调好，是下跌的跳空结构（44% 无可卖档位）+ 瞬时抽空
  （恢复组 p25 停留 1s）让它无法工作。
- **结算清盘守卫必须做。** 它不是止损，是任何自动卖出逻辑的前置条件。
  没有它，`bid=0` 会让赢的单子走上卖出路径。

### 9.10 入场价高低都无解：赔率优势被胜率抵消

> **数值已作废，见 9.18。** 本节的胜负口径是 `maxBid>=0.99` 代理，它有 10 个假阴性；
> 且量的是 `percent_change` 复刻信号，生产实际跑 `goal_surge`。用真实触发 + 链上结算真相
> 重测后，入场价**有**明确趋势且存在悬崖：0.99 以上显著为负（CI [−0.149,−0.019]），
> 0.80~0.90 显著为正（CI [+0.073,+0.123]）。本节「maker 比 taker 逆向选择更强」的
> 机制结论仍成立。

9.1 的「挂越低越差」还有一层：挂单（maker）与吃单（taker）是两个完全不同的群体，
必须分开量。

- **maker**（`m5joint.mts`）：把买单挂在 E 等成交。挂 0.95 胜率 68.8%、挂 0.85 只有 50.0%。
  价格跌到 E 才成交，逆向选择更强，不是更弱。
- **taker**（`m6taker.mts`）：信号时 ask 本来就 ≤E，立刻吃掉。这才是「爬升途中低价买入」
  的真实机制，也是 `maxBuyPrice` 在管的事。

taker 各档：

| ask 上限 | 成交 | 平均成交价 | 胜率 | 无止损期望值 | 加最优止损 |
|---|---|---|---|---|---|
| 0.99（不限） | 65 | 0.862 | **70.8%** | −0.1544 | −0.0722 |
| 0.95 | 40 | 0.789 | 62.5% | −0.1643 | −0.0801 |
| 0.90 | 25 | 0.704 | 52.0% | −0.1840 | −0.0508 |
| 0.85 | 20 | 0.661 | 50.0% | −0.1615 | **−0.0435** |

**平均成交价从 0.862 降到 0.661（赔率大幅改善），胜率同步从 70.8% 掉到 50.0%，

便宜 = 概率低。

这推翻了 9.7 的建议：**「入场价往下走」在赔率上讲得通，但换来的胜率损失刚好抵掉收益。**
买贵和买便宜都不创造优势，因为价格已经把概率定进去了。真正的优势只能来自

两个必须记住的保留：**66 个组合无一为正**；那些「最优」配置都在误杀 80~100% 的赢单，

### 9.11 已落地：深度补拉 + 卖出守卫

**盘口深度定期补拉**（`bookRefreshIntervalMs`，默认 30s）。
成因不是没建列——`price_bot_logs` 早就有 `best_bid_size` / `best_ask_size`，
INSERT 也在写。是 WS 的 `best_bid_ask` / `price_change` 只带价不带量，
只有 `book` 全量快照有；而 `updatePriceAndEvaluate` 里的 size 继承要求
**价位不变**（`prev.bestBid === bestBid`），价格一动就作废。
于是历史数据 bid size 覆盖率 10.7%、ask 侧 7.4%。
现在定期主动拉一次 REST `/book` 补深度，断联期兜底轮询已在高频拉全量 book 时跳过。

**卖出前的盘口守卫** `classifyBookState()`（`auto-trade.ts`，8 个单测）。
它不是止损——9.4 已证明价格止损期望值为负——而是任何自动卖出逻辑的前置：
先确认「现在这个 bid 是真的」。四种状态：

| 状态 | 判定 | 可卖 |
|---|---|---|
| `settlement-cleared` | 规则已完结，或 bid≤0.02 且 ask≥0.99 | 否 |
| `bid-vacuum` | bid 归零（ask 在中间价位），或 bid≤0.6 而 ask≥0.9 | 否 |
| `no-book` | 两边都无报价 | 否 |
| `normal` | 其余 | 是 |

判定顺序有讲究：`settledAt` 优先于价格形态；**买盘归零先于按 ask 分因**。
38693 条历史采样回放（`m7guard.mts`）：

- 前一帧 ≥0.97 的清盘帧（**赢单**）11 个 → **100% 拦住**。这一项漏一个就是把赢单在 0 附近抛掉。
- `bid≤0.02` 的帧 850 个 → **100% 判为不可卖**。
- 分布：normal 91.01% / bid-vacuum 8.46% / settlement-cleared 0.53%。

回放过程中改掉一个真 bug：最初只判「bid 归零**且** ask 在 1.00 附近」，
而 850 个归零帧里有 609 个 ask 落在 0.02~0.99（如 `bid=0 / ask=0.87`），
会被当成正常盘口放过去，然后向空买盘挂卖单。改成 bid 归零一律不可卖、
再按 ask 分因写 reason。

### 9.12 紧止损：算术成立，但价差先把它打掉

前面 9.4 / 9.9 测的止损位是绝对价（0.80/0.70/0.60/0.50）。**对 0.95 的入场价来说这是荒谬的**——
那是每笔冒 15~45 个点的风险。真实操作里买 0.95，止损挂 0.92、0.93。这一节按
`止损价 = 入场价 − d` 重测（`m8tight.mts`、`m9spread.mts`、`m10robust.mts`）。

**算术先摆清楚。** 有止损的二元单，盈亏平衡胜率 = `d / (d + (1 − 入场价))`：

| 入场 0.95，止损距离 d | 盈亏平衡胜率 |
| --- | --- |
| 无止损（亏光） | 95.0% |
| d=0.15（止损 0.80） | 75.0% |
| d=0.03（止损 0.92） | **37.5%** |
| d=0.02（止损 0.93） | **28.6%** |

95% → 29%。所以「买高价筹码必须配紧止损」这个原则本身完全正确，
是我此前把止损位设错了才测出负值。

**但在这批盘口上机制被价差先打掉。** maker 0.95 的 16 笔成交，
成交瞬间 `入场价 − bid` **中位 0.090、均值 0.136、最大 0.660**：
买在 ask 0.95 时 bid 通常已在 0.86。止损挂 0.92 **在成交那一刻就已经在 bid 底下**。

| 配置 | 成交时价差中位 | d=0.03 触发 | 其中开仓即触发 | 跳空滑点均值 |
| --- | --- | --- | --- | --- |
| maker 0.95 | 0.090 | 15/16 | **12** | 0.119 |
| maker 0.92 | 0.030 | 20/22 | 13 | — |
| maker 0.90 | 0.040 | 20/23 | 13 | — |
| taker ask≤0.99 | 0.068 | 63/65 | 54 | — |
| taker ask≤0.95 | 0.050 | 38/40 | 32 | — |

滑点均值 0.10~0.12 意味着**挂 0.92 实际成交在 0.80**，`d` 名义 0.03、实际 0.15。
最差的一笔成交时 bid 只有 0.56，滑点 0.36。

`classifyBookState` 在紧距离上**完全不起作用**（d=0.02/0.03/0.05 时裸跑与带守卫数字逐位相同），
只有 d=0.12 才有差别（−0.1369 → −0.1225）。它拦的是买盘归零，
而这里打掉止损的是「买盘还在、只是本来就低」。

**价差窄的那两笔正是按预期工作的**：

- rule 342 成交时 bid 0.94（价差 0.01）→ 止损在 0.92 正常触发，−0.035。持有是 **−0.95**。
- rule 407 成交时 bid 0.93（价差 0.02）→ 未触发，赢 +0.05。

于是加价差闸门重测（`m9spread.mts`，入场条件改为「信号后第一个 `ask−bid ≤ S` 的时刻」）：

| 价差闸门 | 成交 | 平均入场 | 持有胜率 | 无止损 | 最优 d | 最优期望值 |
| --- | --- | --- | --- | --- | --- | --- |
| ≤0.01 | 26 | 0.743 | 65.4% | −0.0890 | 0.05 | **+0.0547** |
| ≤0.02 | 50 | 0.803 | 68.0% | −0.1232 | 0.05 | −0.0138 |
| ≤0.03 | 55 | 0.825 | 69.1% | −0.1344 | 0.02 | −0.0106 |
| ≤0.05 | 62 | 0.828 | 71.0% | −0.1185 | 0.03 | −0.0246 |

「开仓即触发」随闸门收紧而消失：d=0.02 时价差≤0.05 组 53/62 笔即时触发，
价差≤0.01 组 **0 笔**。诊断得到确认。

**但那个正号站不住，而且闸门做的不是它名字说的事**（`m10robust.mts`）：

- 剔掉最赚的 1/2/3 笔 → +0.0313 / +0.0080 / **−0.0103**。三笔翻负。
- bootstrap 20000 次：95% 区间 **[−0.0127, +0.1375]**，0 在区间内（为正概率 93.6%）。
- **「等价差收窄」实际是「等价格跌下来」**：19/26 笔成交价比信号价低 >0.02，**0 笔更高**；
  信号时 ask 均值 0.844 → 成交 0.743；等待中位 281s、均值 760s
  （rule 374 等了 1.7 小时，入场从 0.92 掉到 0.36）。

**真正稳的是止损本身。** 同一批 26 个 rule 信号即吃单、不等价差：
无止损 −0.1904 → 配 d=0.05 后 **−0.0690**，差额 **+0.1238**。
这个 +0.12 在 m8 / m9 的全部配置里数值几乎一致，机制清楚：
把 −0.97 / −0.92 / −0.82 / −0.69 / −0.57 / −0.47 这些全损压到 −0.05~−0.08。

拆开就是：**止损贡献 +0.12，「等便宜」再贡献 +0.12，两者相加才刚过零**。
而「等」平均要等 12 分钟，跟规则「触发即跟进」的前提直接冲突——
这与 9.6 是同一个矛盾的另一面。

**结论。** 紧止损是目前测出来唯一稳定为正贡献的机制（+0.12，八种配置一致），
但单靠它还填不平 −0.15~−0.19 的坑；填平那部分靠的是压低入场价，
而压低入场价只能靠等，等就不是这个策略了。所以：

1. 紧止损可以做，但**必须配价差闸门**，否则 75~85% 的触发是开仓即触发，止损变成开仓即认赔。
2. 闸门阈值应取 `S < d`（价差必须窄于止损距离），这是硬约束，不是调参。
3. 即便如此期望值仍不显著为正，**所以这不构成上线理由**，只构成 9.12 第 5 条的前置改进。

### 9.13 时间止损：15 分钟不行，而且时间止损整体是多余的

9.6 留了个未决问题：时间止损与「利润靠慢涨」的假设冲突。9.9 测的 60s 杀掉 11/11 赢单，
太短是显然的。这里测 15 分钟这一档（`m11time.mts`、`m12which.mts`）。

**决定性的不是期望值，是赢单与亏单的时间分布能不能分开。** taker ask≤0.99，73 笔（赢 52 / 亏 21）：

| | p10 | p25 | 中位 | p75 | p90 |
| --- | --- | --- | --- | --- | --- |
| 赢单到达 0.99 的耗时 | 16s | 61s | **7.4min** | 27.3min | 48.9min |
| 亏单跌破「入场价−0.10」 | 0s | 0s | **13s** | 5.9min | 14.8min |

中位数差 34 倍，**分布确实分得开**——亏损几乎立刻暴露，利润要慢慢长。
这一点支持「用时间做判据」的直觉。

**但 15 分钟正好落在最差的位置：**

| 时长 | 赢单已完成 | 会砍掉的赢单 | 亏单已暴露 |
| --- | --- | --- | --- |
| 60s | 25.0% | 39 | 60.0% |
| 5min | 46.2% | 28 | 70.0% |
| **15min** | **61.5%** | **20** | **95.0%** |
| 30min | 80.8% | 10 | 95.0% |
| 60min | 92.3% | 4 | 100.0% |

到 15 分钟时亏单已经暴露了 95%——**它抓不到新的亏损了**，
而赢单还有 38.5% 没跑完，于是纯粹在砍利润。期望值随时长非单调正说明这点：

```
纯时间止损   5min = -0.0793      15min = -0.1038      30min = -0.0965
```

15min 是三档里最差的（ask≤0.95 组、两个价差≤0.02 组同样如此）。
15min 逐笔看：砍掉 **18 个赢单 / 11 个亏单**。净差额 +2.76 是因为救下的
rule 342（−0.98→−0.04）、rule 371（−0.91→−0.06）、rule 326（−0.86→−0.08）单笔太大，
但那三笔紧止损也能救，且救得更早更便宜。

**更根本的问题：时间止损在紧止损之外没有增量。** 四组配置一致：

| 配置 | 无止损 | 纯紧止损 | +5min | +15min | +30min |
| --- | --- | --- | --- | --- | --- |
| ask≤0.99 | −0.1416 | **−0.0981** | −0.1023 | −0.1026 | −0.0981 |
| ask≤0.95 | −0.1549 | **−0.0711** | −0.0726 | −0.0738 | −0.0711 |
| ask≤0.99 价差≤0.02 | −0.1232 | **−0.0138** | −0.0177 | −0.0206 | −0.0138 |
| ask≤0.95 价差≤0.02 | −0.1430 | **−0.0153** | −0.0170 | −0.0188 | −0.0153 |

叠加时间止损要么**恰好等于**纯紧止损（30min——因为它从不先于价格止损触发，
是个不起作用的参数），要么**更差**（5min / 15min——它抢在价格止损之前砍掉了还会涨的单）。
没有一组因为加时间止损而变好。

原因在分布的**前段重叠**：赢单 p10=16s、p25=61s，快赢单和快亏单落在同一个时间区间。
「持有了多久」本身分不开它们；分得开的是**往哪个方向动了**。
而读方向就是价格止损。方向一读，时间就不再携带额外信息。

**所以 9.6 的矛盾是个假矛盾。** 它假定「要么承认靠慢涨、放弃时间止损，
要么坚持时间判据、牺牲利润」。实际是：**时间止损这个工具本身可以整个丢掉**，
不需要在两者之间选。判据用价格（`入场价 − d`，配 `价差 < d` 的闸门），
持有时长不设上限，让盘口而不是时钟决定退出。

> 注意上表所有数字仍为负。这一节解决的是「时间止损该设多久」这个问题（答案：不设），
> 不改变 9.12 的结论——紧止损贡献稳定但填不平坑。

### 9.14 只用挂单买入：价格优势真实且显著，但被逆向选择吃掉九成

> **数值已作废，见 9.18.5**（同样的两个前提错误）。机制结论不变，而且在真实闸门参数下
> 更干脆：持有时长从 30 秒扫到 600 秒结果完全不变，放行的每一笔都是立即成交，
> 挂着的那条腿从来没成交过。**买入方式应以吃单为主。**

问题：只用挂单买筹码、止损交给人工判断，**买入方式本身**能不能提高收益。
（`m13maker.mts`、`m14paired.mts`）

Polymarket 无手续费（代码库中没有任何 fee / rebate 口径），所以 maker/taker
的差别纯粹是**价格 × 成交概率**，不含返佣补贴这一项。

成交模型：挂买单在 p，当 `bestAsk ≤ p` 时成交于 p——书被穿越必然发生成交。
忽略排队位置，因此**成交率偏乐观、价格一侧无偏**。

**配对检验：同一个 rule 上挂单必然更便宜，且显著。** 77 个信号，只取两者都成交的：

| 报价方式 | 配对样本 | 差额均值 | 95% 区间 | |
| --- | --- | --- | --- | --- |
| `inside`（ask − 1 tick） | 53 | +0.0365 | [+0.0191, +0.0602] | ★ 显著 |
| `improve`（bid + 1 tick） | 43 | **+0.0822** | [+0.0495, +0.1214] | ★ 显著 |
| `join`（挂在 bid） | 37 | +0.0870 | [+0.0544, +0.1289] | ★ 显著 |

这是整份分析里第一个统计显著为正的结果。但要理解它为什么**必然**显著：
配对差额在同一 rule 上就等于入场价差（赢单 `(1−mk)−(1−tk)`、亏单 `(−mk)−(−tk)`，
都等于 `tk−mk`）。**挂单一定付得更少，这是构造保证的，不是发现。**

真正的问题从来不是「是否付得更少」，而是「少付的够不够抵掉成交筛选的代价」。
答案在总量分解里（`improve` 静态，43 笔成交）：

```
挂单成交的那批 rule，若改吃单   = -0.2157   ← 坏单组合
挂单的价格优势                  = +0.0822
                               ─────────
挂单实际每笔期望值              = -0.1334   （实测 -0.1334 ✓）

吃单在它自己的 73 笔上          = -0.1416
                               ─────────
净差额                          = +0.0082
```

挂单成交的那 43 个 rule 对吃单而言值 −0.2157，比吃单整体的 −0.1416 差 **0.0741**
——这就是逆向选择的代价，它吃掉 +0.0822 里的**九成**，净剩 +0.008。
`join` 同理：−0.2495 + 0.0870 = −0.1625。

**「每信号」那一列的改善是资金混淆，不是买入方式。** `improve` 每信号 −0.0745
远好于吃单 −0.1342，但那只因为它在 55.8% 的信号上才动手。对照组：
**吃单半仓每信号 −0.0671**，比挂单还好。少投钱当然少亏，那不叫收益提高。

**超时吃单救不回来。** 想「拿到价格优势又不漏赢单」：

| 策略 | 成交率 | 均价 | 每笔 | 挂单成交占比 |
| --- | --- | --- | --- | --- |
| 吃单（基准） | 94.8% | 0.854 | −0.1416 | 0% |
| `improve` 纯等 | 55.8% | 0.738 | **−0.1334** | 100% |
| `improve` → 30s 吃单 | 79.2% | 0.837 | −0.1649 | 30% |
| `improve` → 60s 吃单 | 75.3% | 0.817 | −0.1451 | 36% |
| `improve` → 120s 吃单 | 70.1% | 0.792 | −0.1439 | 46% |
| `improve` → 300s 吃单 | 62.3% | 0.787 | −0.1624 | 63% |

任何回退到吃单的变体，每笔期望值都回到 −0.14~−0.17，不优于纯吃单。
漏掉的恰好是直接涨走的赢单，回退时只能在高价补进。

**结论，分三层：**

1. **挂单确实提高每笔收益，+0.04~+0.09，统计显著。** 这条是真的。
2. **但总量上只净剩 +0.008**（−0.1416 → −0.1334），因为挂单优先在坏单上成交。
   **单靠改买入方式不会让策略转正。**
3. **在「止损交给人工」这个前提下，结论要改写。** 逆向选择的代价是「你成交在了坏单上」
   ——而人工判断正好处理这件事：成交后由人决定是否留。机器拿不到的那 0.0741，
   人可以拿回一部分。**所以配人工止损时，改挂单是值得做的**：
   它把 +0.08 的价格优势变成可支配的，而把选择问题交给人。

**推荐 `improve`（bid + 1 tick），不是 `join`：**

- `join` 的 +0.0870 略高，但要排在已有买单队尾，等待中位 **221s**，
  且模型忽略排队位置——真实成交率会明显低于 48.1%。
- `improve` 自己开一个新价位、排在最前，+0.0822 几乎一样，
  成交 55.8%，等待中位 **67s**。
- `inside` 成交最快（19s）但只省 0.0365。

> **模型局限**：忽略排队位置，成交率偏乐观（对 `join` 尤其）；
> 假设报价量总能被完全吃掉。价格一侧无偏，所以 +0.08 这个数可信，
> 成交率那一列要打折看。

#### 9.14 的落地记录

参数：`buyOrderMode: 'taker' | 'maker'` + `makerTickOffset`（默认 `taker` / `1`）。
优先级同其他下单参数：规则级 > 全局 `autoTradeDefaults` > 内置默认。
前端「自动下单」面板有下拉框，选挂单时「穿价缓冲」自动换成「挂高几个 tick」。

**默认没有打开。** 改动交易语义的开关不该默认生效，尤其它把成交率砍掉四成。

三件当时想清楚了的事：

1. **交易通道不需要改。** `placeOrder` 本来就发 GTC（`trading.ts:149`），
   不穿价的限价单自然挂在盘口上。改动只在报价函数里。
2. **不做追价。** `maxOrdersPerRule` 默认 2，撤了重挂就没有下单额度了；
   而且数据本来就说静态挂单（+0.0822）好过追价（+0.043）。
3. **撤单卫生 ≠ 止损。** maker 特有的风险是「机会已经结束，单子还挂着」——
   规则完结/停用/删除/停止监控、机器人停机，这五条路径都会撤掉**未成交**的买单。
   这是纯机械动作，不含任何「该不该继续持有」的判断；已成交的持仓一律不动。
   结算前价格跌穿买价而成交，那不是 bug，那正是量出来的逆向选择（−0.0741）。

**没有做的**：两个方向的回退都不做——超时改吃单（9.14：任何时长都把优势还回去）、
先吃单再退挂单（9.15：一笔也接不到，增量恰好 0）；
卖出/止损逻辑（`classifyBookState` 至今仍只是纯函数加测试，没接入任何调用路径）。

### 9.15 先吃单、吃不成再挂单：一笔也接不到

9.14 测的是「挂单优先、超时吃单」（结论：任何时长都把优势还回去）。
这里测反向：吃单作主腿，被拦下时退到挂单。脚本 `m15takerfirst.mts`、
`m16whyno.mts`、`m17blocked.mts`。

| 策略 | 成交 | 成交率 | 均入场 | 均收益/笔 |
| --- | --- | --- | --- | --- |
| 纯吃单 | 66/77 | 85.7% | 0.8158 | −0.1188 |
| 纯挂单 `improve` | 41/77 | 53.2% | 0.7377 | −0.1524 |
| **先吃单→退挂单** | **66/77** | **85.7%** | **0.8158** | **−0.1188** |

相对纯吃单的增量 **+0.0000/信号，0 笔有差异**。退挂单腿成交 **0/11**。

**为什么一笔也接不到。** 吃单被拦的 11 笔里，窗口内**曾经有快照过闸门的：0/11**
——不是时点问题，拦下的盘口状态整个窗口都成立。而挂在下面的买单接不到货，
因为价格是往上跑的。以 rule 328 为例：bid 从 0.780 涨到 0.999，ask 始终 0.990~1.000，
价差确实收窄到 0.0010，但是**向上收窄**——bid 涨上去贴 ask，不是 ask 跌下来贴你。
静态报价和「跟随 bid 每 tick 重报价」两种都测了，**都是 0/11**。

> 与 9.14 那个回退的区别在这里：9.14 的回退至少会触发，只是把价格优势还回去；
> 这个回退连触发都做不到。**两条腿在同一种盘口状态下同时失效**，
> 不是互补关系——所以链起来不可能好过单腿。

**顺带量出闸门是有效的。** 那 11 笔若无视闸门直接吃：

| | 均收益/笔 | 赢率 |
| --- | --- | --- |
| 闸门拦下的 11 笔（无视闸门吃） | **−0.2649**（CI [−0.5418, +0.0087]） | 8/11 |
| 闸门放行的 66 笔 | −0.1188 | 46/66 |

赢率 73% 高于整体，但入场价在 0.99~1.00，8 个赢单每笔只回 +0.01~+0.026，
3 个输单各 −1.00。**这里必须读入场价而不是赢率**，否则会把捡钢镚看成优势。

**实操上的区别**：以上「吃单失败」指**闸门拦下**。实盘还有另一类失败——
交易所拒单 / 规模填不满 / 余额不足。那种情况下退挂单不算无理，但那是另一件事，
且余额不足时退挂单只是把失败的吃单变成同样付不起的挂单。

### 9.16 盘口挂单量比：方向真实，但显著性没扛住样本翻倍

> **数值已作废，见 9.18**（同样的两个前提错误）。「不要上量比闸门」的结论不变——
> 9.18 找到的有效判据是价格区间，不是盘口量比。

问题：能不能用 bid / ask 的挂单量辅助判断买入信号。

**结论：不要上闸门。** 方向是稳的，但赚不到钱，而且第一次测出来的显著性
在样本翻倍后消失了。

先说方向。量比 = bid 挂量 / ask 挂量，在价格闸门内（`bid>=0.6` 且价差 `<=0.1`）：

| 条件 | 笔数 | 赢 | 均收益 |
|---|---|---|---|
| 无深度闸门（基线） | 31 | 23 | −0.1538 |
| 量比 ≤ 1（卖盘更厚） | 15 | 13 | **+0.0060** |
| 量比 > 1（买盘更厚） | 16 | 10 | **−0.3036** |

方向和直觉相反但机制说得通：**ask 厚 = 卖单还没被吃掉 = 价格还没被推上去**。
量比大反而是「已经涨过了」的痕迹。旁证一致——bid 挂量门槛越高越差
（≥50 → −0.1096，≥100 → −0.1435，≥200 → −0.1763），单调恶化。

**然后是不能上的三个理由。**

**一、显著性没扛住。** 第一次测（n=17、亏损仅 2 笔）精确排列检验 p = 0.0010，
看着很硬。补到 n=31、亏损 8 笔后重跑，**p = 0.051**——连未校正的 0.05 都刚够不上，
离 12 个条件的 Bonferroni 阈值 0.0042 差一个数量级。
那个 0.0010 是压在 2 个亏损样本上的假象。

*教训*：亏损样本数才是这类测量的有效样本量。31 笔里 23 笔是 0.9x 入场、
回 +0.01~0.03 的赢单，它们对均值的贡献几乎是常数；真正决定结论的是那 8 笔 −0.9 左右的亏损。
下次看到「n 够大但亏损只有个位数」，先别相信 p 值。

**二、好的那一半也只是打平。** 量比 ≤ 1 是 **+0.0060**，不是第一次报的 +0.1389。
砍掉一半机会（16/31）换一个打平的子集，不值得。

**三、和入场价纠缠得更紧了。** Spearman 从 0.473 升到 0.536；
量比 ≤ 1 组平均入场价 0.8607，> 1 组 0.9286。

不过分层之后效应**没有消失**，这是唯一让它还值得记一笔的地方：

| 分层 | 量比 ≤ 1 | 量比 > 1 | 差 |
|---|---|---|---|
| 入场价 ≥ 0.9 | −0.1217 (n=6) | −0.3249 (n=14) | 0.2032 |
| 入场价 < 0.9 | +0.0911 (n=9) | −0.1550 (n=2) | 0.2461 |

两层里差距都还在 0.2 上下，说明量比不是入场价的纯代理。但每层只剩个位数样本，
不能当证据用，只能当「值得继续攒数据」的理由。

**顺带一个比量比更值得注意的数**：这 31 笔的基线是 **−0.1538/笔**，
23 赢 8 亏却是负的。赢单全在 0.9x 入场只回几分钱，8 笔亏损各亏 ~0.9。
这就是 9.10 的赔率/胜率抵消，样本变大后更明显了——
**闸门内的整体期望值是负的**，这比「量比能不能加分」是更大的问题。

**与现有 `minBidSize` / `minAskSize` 的关系**：那两个是绝对量门槛，
防的是「盘口太薄下不进去」，且实现上是「未知即放过」（`price-bot.ts:1349`），
长期形同虚设。和这里测的相对量比是两件事，不要混。

覆盖率现在还在爬：两边都有量的采样占比 8-27/28 是 1.4~1.9%，8-29/30 是 5.0~5.2%，
8-31/9-1 到 14.1~14.9%。`buy_signal` 时刻两边有量的从 120 涨到 208 条。
再攒一倍（亏损样本到 15~20 笔）可以再测一次，届时看 p 值稳在哪一边。

脚本：`m22depth.mts` / `m23depth2.mts` / `m24depth3.mts`（主测量）、
`d8sig.mts`（精确排列检验 + 入场价分层）。

### 9.18 结算真相回填后重做：前面的 EV 全部作废，真信号是正的

这一节推翻 9.10 / 9.14 / 9.16 的数值结论（机制结论仍成立）。原因是两个叠在一起的
前提错误，任何一个都足以让 EV 失去意义。

**错误一：判「赢」的口径是个代理，不是真相。** 之前唯一可用的胜负判据是价格日志里
出现过 `bid >= 0.99`。在当时能回填链上结算的 43 条规则上它精确率 100%（29/29 无一例外），
看着无懈可击。但那个 100% 是**只有 4 条可结算亏损**造成的假象——把覆盖率提到 100%
之后，它有 1 个假阳性和 **10 个假阴性**：这 10 条链上结算为 YES 的规则，最高 bid 只到
0.60~0.98，监控在价格涨上去之前就停了，于是全被算成亏损。所有 EV 因此系统性偏悲观。

为什么之前拿不到真相，两条独立的原因：

1. `fetchTodaysSoccerEvents` 用 `active:true, closed:false` 且只取 48 小时窗口，
   **已结算盘口按定义永远不在结果里**。172 条 `buy_signal` 规则里 129 条拿不到链上真相，
   其中 117 条的盘口行最后一次同步发生在开球之前。
2. `soccer_markets` 以 `ON DELETE CASCADE` 挂在 `soccer_events` 上，而
   `deleteClosedEvents()` 每轮同步都删掉 `event_status='closed'` 的赛事，结算价随之消失。

所以真相必须落在规则行上，不能只靠 `soccer_markets.outcome_prices`。已落地：
`price_bot_rules` 加 `settled_outcome` / `settled_price` / `outcome_synced_at` 三列，
`fetchMarketByIdFromGamma()` 按 market id 直查（**必须用路径式 `/markets/{id}`**——
查询参数式 `/markets?id=` 返回空数组，而 `?token_id=` 被 gamma **静默忽略**并返回 20 个
无关盘口，当成命中就会把别人的结算价写进我们的规则），`syncRuleOutcomes()` 负责回填，
`POST /api/bots/price-bot/rules/sync-outcomes` 触发。实测回填 **175/175，覆盖率 25% → 100%**
（134 YES / 38 NO）。**真实亏损样本从 2 笔涨到 38 笔，有效样本量 ×19。**

顺带确认价格日志不能当结算源：46 条序列结尾在 0 附近，其中 11 条从 0.999 直接跳到 0.000。
规则 329 链上结算是 `[1,0]`、`market_status=closed`，日志却收在 0.000——那是退市假象。

**错误二：复刻的信号根本没在生产跑。** 生产用 `rule_type='goal_surge'`（172 条规则，
8 秒窗口 / 净涨 0.02 / 跳空 0.05）。我前面几轮复刻的是 `percent_change` 20%/30s——
那个类型总共只有 3 条规则，而且**全是 `alert` 不是 `buy_signal`**。差别落在入场价上：
`goal_surge` 8 秒窗口能吃到阶梯上行的**第一段**，真实均价 0.7809；30 秒 /20% 的复刻要等
涨幅累积够才触发，均价 0.9033——系统性地买晚了、买贵了。这就是为什么复刻测出 −0.1241，
而真实触发是 **+0.0723**。

#### 9.18.1 真信号：不用重建，它本来就是正的

真实 `goal_surge` 触发，每规则取首次，n=109（100% 结算覆盖）：

| | 值 |
|---|---|
| 胜 / 负 | 93 / 16 |
| 胜率 | **85.3%** |
| 均价 | 0.7809 |
| 盈亏平衡所需胜率 | 78.1%（= 均价） |
| EV / 份 | **+0.0723**（⚠ 偏高，见 9.21：按成交口径约 +0.047） |
| 自助法 95% CI | **[+0.0053, +0.1348]** |
| P(EV>0) | **98%** |

> **9.21 的修正**：本节按 `status='placed'` 统计，而 placed 不等于成交——
> 20 个 token 挂着没成交就被撤了，其中 18 个结算为 YES，被当成足额赢家计入。
> 链上实现的边际是 **+5.4% / 约 +4.7 分每份**。胜率 85% 不变，每笔边际打七折。

胜率高出平衡线 7.2 个百分点，**且 CI 整体在零以上**——这是整份文档里第一个
「策略级别为正且统计显著」的结论。（96% 覆盖时 CI 下沿还是 −0.0046，补完最后 7 条
才推过零；那 7 条全是 YES。样本量的边际价值在这里非常直观。）
**第一问的答案：信号本身不需要重建。** 需要动的是闸门，见下。

实际下单的 58 笔（`status='placed'`）：胜率 **93%**、均价 0.857、EV **+0.0736**、
CI [−0.003, +0.137]。对照 skipped 的 2262 笔胜率只有 77%——**闸门确实在选好单**，
被放行的比被拦下的好 16 个百分点。这是现有风控的正面证据。

#### 9.18.2 闸门的反事实 EV：拦对了什么，拦错了什么

`price_bot_orders` 在 `status='skipped'` 的行上也存了 `limit_price` / `best_bid` /
`best_ask`，所以每一次拒单都能算反事实盈亏：若当时真按 `limit_price` 吃进去，结算后赚多少。
2346 条有结算真相的下单记录，按原因归类（「全部触发」口径，单笔 EV）：

| 拒单原因 | n | 胜率 | 均价 | 反事实 EV | 判断 |
|---|---|---|---|---|---|
| 限价 ≥ 上限 0.97，利润空间不足 | 735 | 89% | 0.988 | **−0.0953** | 拦对了 |
| 该盘口已下单 2 笔，达上限 | 563 | 93% | 0.816 | **+0.1147** | **拦错了** |
| 盘口价 < 下限 0.6，离结算尚远 | 465 | 28% | 0.395 | **−0.1133** | 拦对了 |
| DRY-RUN（盘口未开自动下单） | 194 | 82% | 0.860 | −0.0406 | — |
| 价差 > 上限，穿价买入会显著溢价 | 160 | 93% | 0.856 | **+0.0753** | **拦错了** |
| 价差 > 上限，挂单逆向选择最重 | 100 | 78% | 0.801 | −0.0208 | 边缘 |

**注意胜率和钱是两件事。** 735 条被 0.97 上限拦下的赢了 89%，听起来拦错了，但均价 0.988——
0.988 入场需要 98.8% 胜率才打平，89% 是实打实亏 −0.0953。这是全表最重要的一条区分。

三条闸门的分档细看：

**`maxBuyPrice: 0.97` —— 拦得最有价值的一条。** 735 条拒单里 613 条限价在 0.99 以上，
那一档 EV **−0.1107**；每规则首次口径 EV −0.0770、**CI [−0.149, −0.019] 整体在零以下**。
0.97~0.98 档 EV +0.0078（≈0），0.98~0.99 档 −0.0467。
**钱全在「拒绝 ≥0.99」这一刀上**，上限设 0.97 还是 0.98 几乎无差别。

**`minBuyPrice: 0.6` —— 该留，但真正有效的区间是 0.40~0.60。** 分档：
0.40~0.50 EV **−0.3455**（胜率 10%，n=49）、0.50~0.60 EV **−0.2084**（33%，n=69）——
这两档在两种口径下都稳定为负，闸门在这里干的是实活。
但 0~0.20（n=105）EV 只有 −0.0212、0.20~0.40（n=136）−0.0778，
每规则首次口径下这两档甚至翻正（+0.0837 / +0.1500，n=8/11，CI 宽得跨零）。
原因是极低价的赔率补偿：0.15 买入赢一次赔 5.7 倍，25% 胜率就够本。
**样本太小，不建议动下限的下半段**，但记录下来：0.6 这条线的价值集中在 0.4~0.6，不是全程。

**`maxSpread: 0.1` —— 建议放宽，但理由是吞吐量不是单笔 EV。** 被它拦下的 160 条
反事实 EV +0.0753，分档 0.70~0.85 是 +0.0610（n=170）、0.85~0.95 是 +0.0456（n=57），
都为正；负的只有 0.60~0.70（n=10）和 0.95+（n=16）两个小档，而后者本来就被 0.97 上限挡住了。
**这正是「限价上限已经包含了价差闸门的作用」**——两个一起叠只会多拦好单。
合并测算：放开价差后从 58 笔 EV +0.0736 变成 311 笔 EV 略降，单笔期望降了，
**总盈亏涨到约 3 倍**。

**`maxOrdersPerRule: 2` —— 机会成本最大的一条，所有分档都为正。**
563 条拒单 EV +0.1147，**比实际成交的 +0.0736 还高**；分档 0~0.6 +0.5340、0.6~0.7 +0.1264、
0.7~0.85 +0.1092、0.85~0.95 +0.1029、0.95+ +0.0442，无一为负。
但要诚实标注一层选择效应：**这些是「已经下过 2 笔的规则上的后续触发」**，
一条规则能反复触发说明价格一直在往上走，也就是进球是真的。所以这个池子是
「对已确认在赢的仓位加仓」，边际优势真实存在，但 93% 的胜率里有一部分是后见之明。

#### 9.18.3 配置敏感度：悬崖只有一处

候选池 = `placed` + 所有非 DRY-RUN 的 `skipped`，n=2098。只按价格区间筛（等价于
「放开价差与配额，只留价格上下限」），格子里是**合计盈亏 / 笔数**：

| 下限＼上限 | 0.96 | 0.97 | 0.98 | 0.99 | 1.00 |
|---|---|---|---|---|---|
| 0.50 | +54.3/1023 | +53.1/1068 | +53.5/1116 | +50.8/1179 | **−17.0**/1802 |
| 0.55 | +58.4/982 | +57.2/1027 | +57.7/1075 | +54.9/1138 | **−12.8**/1761 |
| 0.60 | +63.7/943 | +62.5/988 | +62.9/1036 | +60.2/1099 | **−7.6**/1722 |
| **0.65** | **+76.7**/893 | +75.5/938 | +75.9/986 | +73.2/1049 | +5.4/1672 |
| 0.70 | +68.4/826 | +67.2/871 | +67.6/919 | +64.9/982 | −2.9/1605 |
| 0.75 | +69.1/760 | +67.9/805 | +68.4/853 | +65.6/916 | −2.1/1539 |

读法：**上限那一列的 0.99 → 1.00 是唯一的悬崖**，从 +51~+73 直接掉到 −17~+5。
「不买 0.99 以上」这一条约值 60~75 个单位的盈亏，是全局第一重要的参数。
上限在 0.96~0.99 之间怎么选几乎无差别（差 3 个单位以内），说明**现有的 0.97 已经够好，
不必调**。下限 0.65 是格子里的最优（+76.7），但比 0.60 只多 13 个单位、比 0.70 多 8 个，
这种起伏更像过拟合而非信号，**下限在 0.60~0.75 之间都可以，不值得为 0.65 专门改**。

关键对比：现状实际成交 58 笔合计 **+4.3**；同样的价格区间规则但放开价差与配额，
988 笔合计 **+62.5**。**瓶颈不在选股准不准，在吞吐量——现有闸门把 96% 的机会拦掉了。**
只放开价差闸门这一条（不动配额）：58 笔 → 318 笔，每规则首次口径 EV +0.0788、
**CI [+0.005, +0.141] 整体为正**，比现状的 [−0.003, +0.137] 更硬。

一处必须标注的方法论局限：反事实 EV 假设被拒的单能按 `limit_price` 成交，
**没有计入市场冲击**。被价差闸门拦下的恰恰是薄盘口，真去吃单滑点会比记录的 `limit_price` 差。
所以建议是「放宽」而非「取消」价差闸门，让 0.97 上限去兜底。

#### 9.18.4 尾盘绝杀球：决定因素是价格，不是时钟

第三问。95 分钟后的 626 条下单记录，均价只有 0.548、胜率只有 48%——远低于全样本的 76%。
按价格分档后原因很清楚：

| 95+ 分钟 | n | 胜率 | 均价 | EV | 95% CI |
|---|---|---|---|---|---|
| limit 0~0.4 | 262 | 16% | 0.216 | −0.0517 | [−0.094, −0.007] |
| limit 0.4~0.6 | 100 | 31% | 0.492 | **−0.1820** | [−0.269, −0.091] |
| limit 0.6~0.8 | 56 | 64% | 0.671 | −0.0282 | [−0.149, +0.088] |
| **limit 0.8~0.9** | 29 | **93%** | 0.829 | **+0.1017** | [−0.007, +0.177] |
| limit 0.9~1.01 | 180 | 91% | 0.980 | −0.0690 | [−0.112, −0.030] |

对照 85 分钟之前，形状**完全一样**：0~0.4 胜率 0%（n=3）、0.4~0.6 胜率 50%（n=10）、
0.6~0.8 胜率 65% EV −0.0926、**0.8~0.9 胜率 95% EV +0.1004 CI [+0.076, +0.123]**
（n=351，全表最硬的一个格子）、0.9+ 胜率 92% EV −0.0588 CI [−0.078, −0.041]。

**结论：时段本身不是判据，价格才是。** 真进球会在几秒内把价格推到 0.8 以上；
第 95 分钟还停在 0.5 的「飙涨」不是进球，是薄盘噪音或更低档线的溢出——
胜率 16~31%，EV 显著为负。这也解释了 0.6 下限拦掉的 465 条的分布：
**363 条（78%）落在 95 分钟后，胜率只有 21%，合计 −42.9，CI [−0.159, −0.077] 显著为负。**
换句话说，`minBuyPrice: 0.6` 事实上已经在充当尾盘假信号过滤器，**不需要再加时段闸门**。

反过来说，真正的绝杀球（价格冲到 0.8~0.9）在尾盘的表现和常规时段一样好
（93% vs 94%），**现有策略已经覆盖它了**，不需要为尾盘单独开一套参数。

需要警惕的是 0.9 以上那 180 条：胜率 91% 但 EV −0.0690 显著为负。绝杀球的问题不是
「抓不到」，而是**抓到之后追得太高**。0.97 上限正是在管这件事。

同时说明：9.18 之前那些「70~85 分钟最好」「95+ 最好」的时段结论都不成立。
触发层面 70~85 分钟测出 EV +0.2120 CI[+0.140,+0.265]，但下单层面同一时段只有 +0.0171；
85~95 和 95+ 在两种口径下**符号相反**。时段效应在控制入场价后就消失了，
之前看到的都是入场价效应的投影。**不要上时段闸门。**

（注意 95+ 在触发层面只有 n=6、EV +0.2733 CI[−0.052,+0.583]——那 6 笔均价只有 0.3933，
是「低价买到真进球」的幸存者。下单层面同一时段 626 条里 362 条限价在 0.6 以下、
胜率 16~31%，才是这个时段的真实面貌。**小样本高 EV 的分段一律不要当结论用。**）

#### 9.18.5 挂单 vs 吃单：在真信号下答案更明确

9.14 的机制结论仍然成立（挂单价格优势真实、被逆向选择吃掉九成），但在真实闸门
参数下有个更干脆的观察：**把持有时长从 30 秒扫到 600 秒，结果一个字都没变**——
放行的每一笔都是立即成交，挂着的那条腿从来没成交过。挂单在 bid 上每笔 +0.2037 对
吃单 +0.0233，但成交率只有 8.9%（60 秒）/ 17.7%（300 秒），摊薄后 +0.0087 反而更差。

**第二问的答案：以吃单为主。** 挂单不是不能用，而是在「盘口一确定就要抢」的场景里
结构性地接不到货——我们要的正是别人急着卖的那一刻，而那一刻挂单排在队尾。
两者结合（先挂后吃）已在 9.15 测过：一笔也接不到，增量恰好 0。

脚本：`r19which.mts`（识破信号类型错配）、`r20real.mts`（真实触发 EV + 自助法）、
`r21gates.mts`（闸门反事实 EV，本节主表）、`r22late.mts`（尾盘分层 + 敏感度网格）。
回填：`r15backfill.mts`，落地代码见 `src/bots/price-bot/outcome-sync.ts`。

### 9.20 赛前分大小球再分激进/保守：线与时段共线，且赛前数据方差为零

提案：赛前判断这场是大球还是小球，大球局面用激进参数、小球用保守参数。
测了两条路，都不成立，但**不成立的理由不同**，分开记。

#### 9.20.1 「线」是大球局面的在场证据，但它扛不住时段的控制

先说清楚一件事：**不需要赛前预测就能知道是不是大球局面。** 触发时刻的临界线本身
就是答案——线 0.5 意味着 0 球，线 3.5 意味着已经进了 3 球。这是**已实现**的事实，
没有预测误差，而且免费。所以能测的问题变成：线带不带增量信息。

原始分层看着很像带：

| 线 | n | 胜率 | 均价 | EV | 95% CI |
|---|---|---|---|---|---|
| O/U 0.5 | 39 | 90% | 0.829 | +0.0683 | [−0.055, +0.178] |
| O/U 1.5 | 25 | 84% | 0.821 | +0.0190 | [−0.122, +0.137] |

**控制入场价，效应还在**（三个价格带方向一致，0.75~0.85 带里低线 −0.1027 对高线 +0.1471

必然如此：要进 3 个球才会走到 O/U 3.5 成为临界线。同一时段内比：

| 时段 | 线 ≤1.5 | 线 ≥2.5 |
|---|---|---|
| 0~45 | n=49 EV **+0.0266** | n=7 EV **−0.0330** |
| **45~85** | **n=12 EV +0.1437** | **n=29 EV +0.1401** |
| 85+ | n=3 EV +0.0367 | n=9 EV +0.1011 |

45~85 是唯一两边都有量的格子：**+0.1437 对 +0.1401，差 0.0036,噪音。**
上半场里高线反而更差。反过来在同一线组内比时段，时段的效应稳稳在：
低线组 0~45 → 45~85 是 +0.0266 → +0.1437（5 倍）；
高线组是 −0.0330 → +0.1401（符号翻转）。**两个线组都在 45~85 变好。**

所以 `O/U 3.5 EV +0.2562` 是两件事凑的：高线集中在好的时间窗口，且高线入场价天然便宜
（O/U 0.5 均价 0.829 → O/U 3.5 均价 0.681，单调）。**线本身不带增量信息。**

加线过滤的代价算给出来：45~85 全线 n=41 EV +0.1412；45~85 且线 ≥2.5 是 n=29 EV +0.1401。
**损失 12 笔、EV 不变。纯亏。**

注意这与 9.18.4「不要上时段闸门」并不矛盾但需要并读：那一节是在**下单层面**（含大量
同规则重复触发）测的，时段效应在两种口径下符号相反；这里是**触发首次**口径。
两个层面对时段的结论不一致，所以 45~85 这个窗口**还不足以单独上闸门**，
只能说「线不是那个维度，时段更可能是」。样本再翻倍后重测。

#### 9.20.2 赛前数据的方差是零，提案目前无法实现也无法检验

这一条是独立的硬阻碍，与效应真假无关。109 个触发里**只有 21 个有开球前的价格**，
而这 21 个全部落在同一个桶：赛前 Over 价 0.7~1.01（均值 **0.945**），且全是 O/U 0.5 的线。
**预测变量的方差是零，没有东西可以分层。** 这 21 个的 EV 是 −0.0030。

原因是选择效应，不是采样不足：**规则只在盘口已经接近确定时才被创建**，
所以记到的赛前价永远是「赛前就快 0.95」那一类。采样口径本身就偏。

价格日志层面：开球前 2396 条 / 开球后 45617 条；按规则看，只有 38 条规则有开球前的
日志（19 条在开球前 10~60min，16 条在 >60min，3 条在 0~10min），115 条规则的日志
从开球后才开始。最早的一条在开球前 210 分钟。

联赛维度同样用不了：109 条里 65 条的 `league` 就是笼统的「足球」，有名字的联赛
n=5~18（Japan J League n=5 EV −0.3760、J2 n=6 EV +0.1617——这种量级不能当结论）。
`soccer_markets.outcome_prices` 是单行覆盖（`ON UPDATE`），也没有赛前快照。

**要让这个提案变得可测，需要先补三样数据**（都是采集侧改动，不是分析能补的）：

1. **赛前 O/U 全档报价快照**，不只是已接近确定的那条线。现在的规则创建逻辑天然只看
   临界线，得另开一条赛前采集路径。
2. **实际比分/进球时间**。现在库里没有任何比分字段（9.18 已确认没有结算或比分列，
   `settled_outcome` 只有 yes/no）。没有比分就无法定义「大球比赛」的真值，
   只能用线反推，而线又与时段共线。
3. **联赛的规范化标注**。60% 的记录只有「足球」。

在这三样补齐、且每个赛前分层里亏损样本攒到 15~20 笔之前，这个方向没法验证。

脚本：`r23pre.mts`（线/联赛/成交量分层 + 入场价控制）、
`r24line.mts`（线与时段的共线检验 + 赛前价预测力）。

### 9.21 实盘「损失惨重」的归因：亏的不是这个信号，而且我的 EV 又高估了一次

反馈是「又测试了几场比赛，损失惨重，感觉全是误买入」。用链上流水
（`data-api.polymarket.com/activity`，全历史 148 条，2026-08-24 ~ 09-02）核对的结果，
两个判断都不成立，但暴露出我自己的第三个测量前提错误。

**总账（链上，不含未结算占款 $64.35）：**

| 项 | 笔数 | 金额 |
|---|---|---|
| 买入 | 79 | −$319.94 |
| 卖出 | 23 | +$126.44 |
| 赎回 | 46 | +$194.00 |
| **净** | | **+$0.50** |

**按来源归因**（键必须用 `conditionId` + `outcomeIndex`，见下方坑）：

| 来源 | 仓位 | 买入 | 收回 | 净 | 赚/亏 |
|---|---|---|---|---|---|
| 价格机器人（只做 O/U） | 47 | −$226.81 | +$239.13 | **+$12.33** | 40 / 7 |
| 让分·赢球·平局·双方进球 | 30 | −$93.13 | +$81.31 | **−$11.83** | 10 / 20 |

那 30 个亏钱仓位（$90.38，买在 0.37~0.67）在 `soccer_orders` 里命中 40 条、在
`price_bot_orders` 里命中 **0 条**。`price_bot_orders` 中 `status='placed'` 的单
**100% 落在 O/U 盘口上，无一例外**。所以亏损来自足球页/价值机器人那条路径，
不是这里的买入信号。价格机器人本身 47 仓位 40 胜 7 负（85%），ROI +5.4%。

**错误三：`status='placed'` 不等于成交。** 它只表示「提交且交易所受理」。66 个 placed 的
token 里 **20 个在链上查不到任何成交**，它们在 `soccer_orders` 里的状态是
`cancelled`（22 笔，均价 0.894）和 `failed`（3 笔）；有成交的那批则是
`filled` / `settled`。原因在 `price-bot.ts:2196`：规则标记完结时
`cancelRestingBuyOrders()` 会撤掉还挂在盘口的买单——**这是正确行为**（结算后代币归零，
挂着的买价会被人拿废票砸），而且注释已写明 taker 单也可能因报价落后于 ask 而挂上。

后果是 9.18 的 EV 偏乐观：那 20 个未成交 token 里 **18 个链上结算为 YES**，被当成
足额盈利的赢家计入。链上实现的边际是 $12.33 / $226.81 = **+5.4%，约 +4.7 分/份**，
而不是 9.18 报的 **+0.0723/份**。胜率 85% 这个结论不变，**每笔的边际要打七折**。

还有一处口径破口：链上 7 个亏损仓位 vs 结算口径的 4 个，差的 3 个是中途卖出止损
（Incheon −$2.12、Pohang −$1.84、Qingdao −$0.67）。9.18 全部 EV 假设持有到结算，
但账上确实有 23 笔卖出，其中多数是 0.999 附近平掉赢家（等价于赎回，无所谓），
少数是真的割在 0.50~0.83。**测 EV 前必须先确认有没有卖出。**

**真正的损失是机会成本，不是误买入。** 116 笔 failed 单的原因 **100% 是
`not enough balance`**，没有一笔是别的原因。钱包现金只有 $2.86~$8.49，而每笔单要
$4.3~$5.0，于是 09-02 一天被拒 106 笔（前几天只有 0~11 笔）。被拒掉的里面有真赢家：
规则 492、502、500、485 的 bid 最终都到了 0.999 / 0.980，单一笔都没进去。
`baseSize` 降到 3 之后单笔只要 ~$4.8，但钱包余额比这还少，所以降 size 并没有解决问题。

**新增的坑（都会静默出错）：**

1. **`activity` 接口的 REDEEM 记录 `asset` 字段是空串**——46 条里只有 13 条带 token id，
   但 46 条全都带 `conditionId`。按 `asset` 归组会把 33 笔赎回丢进空串桶，
   算出来的机器人净额是 **−$111.67**（假亏损），按 `conditionId` + `outcomeIndex`
   归组才得到真值 **+$12.33**。两个数差 $124，方向都反了。
2. **`settled_outcome` 存的是小写 `yes` / `no`**，比 `'YES'` 会静默得到 0 胜 0 负。
3. **`soccer_orders.created_at` 是本地时间（UTC+8），`price_bot_orders.created_at` 是 UTC。**
   同一批下单在两张表里差 8 小时，会被误认成两个不同来源。
4. 胜负要按成交口径统计：`JOIN soccer_orders s ON s.id = o.trade_order_id`
   并排除 `s.order_status='cancelled'`。`db.ts` 的配额计算已经这么做了（见 `db.ts:826`），
   分析脚本也必须跟上。

脚本：`r26fail.mts`（失败原因）、`r27bias.mts`（下单价分布，逆向选择假设**不成立**：
placed 均价 0.8606 vs failed 0.8644）、`r31ledger.mts`（链上台账）、

### 9.21b 买入时刻离进球有多远：0 / 123 笔在确定性之后

图见 **`docs/price-bot-signal-charts.html`**（24 个盘口的 best_bid 曲线，标了触发点、
下单点、到达确定性的时刻，附领先时间直方图）。库里没有比分/进球时间字段，
但盘口都贴在临界线上、一球即结算，所以**价格首次到 0.99 就是进球落地的时刻**。

- **123 笔下单里 0 笔**是在价格已经到过 0.99 之后下的。
- 下单 → 价格首次到 0.99：**中位数 16.7 分钟**，四分位 1.5 ~ 44.8，最长 81。
- 另有 21 笔到监控结束都没到过 0.99。

所以第 1 节写的「吃到进球后的确定性红利」在执行层面没有发生过一次。
`goal_surge` 是 8 秒窗口净涨 0.02 / 跳空 0.05，配上 `minBuyPrice 0.6` ~
`maxBuyPrice 0.97` 的区间，**按定义只能抓到进球之前的动量波动**（危险进攻、角球、射门）：
真进球会让贴线盘口直接跳过 0.97，那批单（n=735，均价 0.988）全部被上限拦掉，
反事实 EV −0.0953。**「进球后的确定性红利」在贴线盘口上本来就不存在——
盘口确定的那一刻，价格就是 1。**

「买得离进球更近是否更好」——不是。n=45 分四档：

| 领先进球 | n | 胜/负 | 均价 | EV/份 |
|---|---|---|---|---|
| 0~3 分 | 14 | 14 / 0 | 0.868 | +0.1321 |
| 3~15 分 | 9 | 9 / 0 | 0.859 | +0.1411 |
| 15~40 分 | 14 | 14 / 0 | 0.833 | +0.1671 |
| 40 分以上 | 8 | 8 / 0 | 0.876 | +0.1237 |
| 全程未到 0.99 | 16 | 11 / 5 | 0.851 | **−0.1637** |

**领先时间完全不带信息**：四档全 100%、无趋势、均价都在 0.83~0.88。
所以不存在「把信号收紧到进球那一刻」这个杠杆。⚠ 前四档的 100% 有循环成分
（「价格到过 0.99」≈「Over 赢了」），这张表只能用来说明**领先时间没有区分度**，
不能当选单依据；最后一档的 5 笔才是真假阳性，其余 11 笔是监控早停的退市假象。

**重新定位这个策略**：它赚钱（链上 47 仓位 40 胜 7 负 / ROI +5.4%），但赚的是
「贴线盘口上还会再进一个球」的方向性判断，不是确定性套利。买在 0.86、胜率 85%，
两个数几乎相等，所以边际薄。要做厚只有两条路：**压低入场价**，
或**提高「球会来」的判准**（筛掉最后一档那 5 笔）。改下单时机没用。

### 9.22 下一轮建议顺序（覆盖第 8 节）

**−1. 先充钱包（当前唯一的硬约束，压倒其他一切）。** 见 9.21：现金 $2.86~$8.49，
   单笔要 $4.3~$5.0，116 笔单 100% 因 `not enough balance` 被拒，09-02 一天 106 笔，
   里面有 bid 最终到 0.999 的真赢家。**在这个状态下调任何参数都没有意义**——
   闸门已经不是瓶颈，钱包才是。按每笔 ~$4.8、目标同时持有 20~30 个仓位算，
   工作资金至少 **$150~$250**；要跑到 9.18 建议的吞吐量（约 900 笔/月）还得更多。

**0. 把结算真相跑起来。** `POST /api/bots/price-bot/rules/sync-outcomes`
   接入定时调用（建议每小时一次）。没有这一列，所有 EV 都是在测一个有 10 个假阴性的
   代理口径——9.18 的三次结论翻转全是这个原因。注意 `listRulesPendingOutcome` 要求
   `end_time < 现在 − 3 小时`，刚结束的比赛要等一轮才回填。
   **另外分析脚本要改成按成交口径统计**（见 9.21 坑 4），否则 EV 会像 9.18 那样偏高三成。

1. ~~补 size 落库~~、~~结算清盘守卫~~ —— 已落地，见 9.11。
   下一轮先**验证 size 覆盖率真的上去了**（重跑 `m4empty.mts`，看 has_bsz 占比）。
2. ~~不要再调入场价参数~~ —— **已被 9.18 推翻。** 入场价是全局第一重要的参数，
   而且只有一处悬崖：**0.99 → 1.00**，值 60~70 个单位的盈亏。现有 `maxBuyPrice: 0.97`
   已经站在悬崖正确的一侧，**不必调**（0.96~0.99 之间差 3 个单位以内）。
   `minBuyPrice: 0.6` 同样该留（0.60~0.75 之间都可以）。
   真正该动的是**吞吐量**：现有闸门拦掉 96% 的机会，58 笔合计 +4.3，
   放开价差与配额后 988 笔合计 +62.5。优先级：
   - **`maxSpread: 0.1` → 先放宽这个**（160 条拒单 EV +0.0753，且 0.97 上限已包含它的
     作用，两个叠着只多拦好单）。单独放开它就能把 58 笔变成 318 笔，
     每规则首次 EV +0.0788、**CI [+0.005,+0.141] 整体为正**，比现状更硬。
     **放宽而非取消**——被它拦的是薄盘口，反事实 EV 没计入市场冲击。
   - **`maxOrdersPerRule: 2` → 提高**（机会成本最大：563 条拒单反事实 EV +0.1147，
     所有分档为正）。但注意这是「给已确认在赢的仓位加仓」，93% 胜率含后见之明成分，
     建议小步放到 3~4 而不是取消，并配合 `maxDailyNotional` 一起看。
3. **止损：绝对价止损不要上，紧止损可以做但先补价差闸门。**
   9.4 / 9.9 的绝对价止损（0.80/0.70/…）测出来为负，是因为止损位本身设错了（见 9.12）。
   按 `入场价 − d` 的紧止损贡献稳定的 +0.12，是目前唯一可复现为正的机制，
   但必须先满足 `成交时价差 < d`，否则 75~85% 的触发是开仓即触发。
   即便如此总期望值仍不显著为正（bootstrap 区间含 0），**不足以单独上线**。
4. ~~决定 9.6 的两条路~~ —— 已化解，见 9.13。**不要上时间止损**（任何时长），
   它在紧止损之外没有增量；15min 尤其差。持有时长不设上限，退出交给价格判据。
5. **买入方式：`buyOrderMode` 保持 `taker`。** 挂单模式已实现且可用（9.14 的落地记录），
   但 9.18.5 的量测很干脆：在真实闸门参数下，持有时长 30~600 秒结果完全不变，
   挂着的那条腿从来没成交过。我们要的正是别人急着卖的那一刻，而那一刻挂单排在队尾。

6. **不要上盘口量比闸门**（见 9.16），**也不要上时段闸门**（见 9.18.4）。

   363 条（78%）落在 95 分钟后、胜率只有 21%。真正的风险是抓到之后**追得太高**
   （0.9 以上 180 条胜率 91% 但 EV −0.0690），那由 0.97 上限管。
7b. **不要按大小球分激进/保守**（见 9.20）。两个理由各自独立且都足够：
   线与时段严重共线（低线 64 条里 49 条在上半场，高线 45 条里 38 条在下半场），
   同一时段内比线差异是噪音（45~85 段：+0.1437 对 +0.1401），
   加线过滤损失 12 笔而 EV 不变；且赛前价只有 21/109 覆盖、全部落在同一个桶
   （均值 0.945，全是 O/U 0.5），**方差为零，无从分层**。

   都是采集侧改动。顺带一条方法论：**「线」不需要赛前预测**，
   触发时刻的临界线就是大球局面的已实现证据，免费且无预测误差。
8. 方向二：**价值推断**。注意 9.10 那个「优势不在入场价位」的前提已被 9.18 推翻——
   入场价恰恰是最重要的参数。所以价值推断不再是「唯一出路」，而是
   「把吞吐量放开之后的下一层优化」。优先级降到闸门调整之后。
9. 钱包充值与 USDC allowance 仍未处理（余额 ≈ $0.089），真跑单前必须先充。
